## Summary
The Husk Network keeps a few counters, plus 60 m zone tallies, in the player's saved profile. Pure functions turn those into behaviour traits and an infrastructure plan, once at the start of each raid.

## Status
Reverse-Documented. Implementation: deployed.

## Context
- The Husk Network is Scrapfall's core pillar (`design/game-brief.md`): Husks have to remember how *this* raider fights across raids and react to it.
- There's no game server. The profile is saved to the browser, or to the Claude page's per-user storage (`accounts.js`), and the player can edit it.
- The memory has to drive three consumers: Husk AI (`enemies.js`), topside infrastructure (`infrastructure.js`, `world.js` build sites) and the Raider Log read-out (`ui.js`).

## Decision
1. **Store raw counts, not conclusions.** `blankMemory()` is a flat object of counters (`seen`, `peaceful`, `provoked`, `hits`, `crits`, `melee`, `longKills`, `closeKills`, `pods`, `kills{type}`…) plus `zones: {"zx,zz": [heat, calm]}` on a 60 m grid, capped at 100 zones. It lives at `profile.network`.
2. **Derive everything with pure functions.** `traits(m)` maps the counters to 0..1 traits (`aggression`, `trust`, `eyeGuard`, `keepAway`, `jink`, `podGuard`, `growth`) and the numbers the AI uses directly (`space` 4–9 m, `patience` 2.6–0.7 s, `rally` 30–75 m, `calm` 12–45 s, `shootFirst` when aggression > 0.7). Each ratio has a +N smoothing term, so a few early encounters can't swing a trait to its limit.
3. **Snapshot per raid.** `game.js:516` computes `this.mind = traits(mem)` once at deploy. Events recorded during the raid (`record*` calls in `game.js`) change the memory but not the current raid's behaviour; they take effect from the next raid.
4. **Decay at raid start.** `startRaidMemory` scales zone heat by 0.85 and calm by 0.9 each raid, and drops zones that fall below 0.2, so old grudges fade.
5. **Infrastructure is planned from the memory.** `planInfrastructure` builds `round(1 + 9·growth)` structures: Bulwarks on the hottest sites, Cradles on the calmest.
6. **Distrust the save.** `cleanMemory` clamps every counter, whitelists Husk types and validates zone keys whenever the profile loads (`inventory.js:134`).

**Rationale — INTENT UNKNOWN (inferred from implementation, not confirmed):** keeping counts (not traits) lets the formulas be retuned without migrating saves. Snapshotting per raid keeps Husk behaviour stable within a run and makes "they learned" a between-raids reveal.

## Alternatives Considered
*Inferred, not confirmed by the author.*
- **Store the traits themselves**: smaller saves, but every tuning change would need a save migration, and the history behind a trait would be lost.
- **Update traits live during a raid**: more reactive, but Husks would change mid-fight, and the Raider Log couldn't explain behaviour as something learned between raids.
- **A server-side shared network across all players**: not possible without a game server (out of scope until co-op/PvP brings one).

## Consequences
- ✅ All learning formulas live in one file, as pure functions, so they're unit-testable without a scene.
- ✅ Retuning is free: change `traits()` and every existing save is read the new way.
- ⚠️ The memory is per-player and client-side, so a player can reset or edit their own network (clamped, not prevented). That's accepted for a single-player game.
- ⚠️ `planInfrastructure` uses `Math.random()`, not the seeded RNG in `rng.js`, so a given memory doesn't always give the same layout.
- ⚠️ Smoothing constants (+4, +6, +30) and thresholds are hardcoded in `network.js`, not in `config.js` like the other balance values.

## Performance Implications
`traits()` runs once per raid start (and once more for the Raider Log); `record*` calls are O(1). Memory is bounded at 100 zones × 2 numbers plus ~15 counters, well under 5 KB per save.
